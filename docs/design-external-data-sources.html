What We're Building

A generic framework that lets customers bring their own data into LiveOps without copying it. Customers point us at tables they already have — in their own S3 buckets, in Snowflake, in Databricks — and our agents can query that data immediately alongside the built-in gaming tables.

Today the solution only works with CSV and JSON files inside our S3 bucket. Every customer has to ETL their data into our format before they get any value. This change removes that requirement.

Why

Reason Detail
Customer demand Customers using Snowflake want to query their existing data through LiveOps agents. They shouldn't have to duplicate data into our bucket first.
Broader applicability Most game studios already have data in a lakehouse (Snowflake, Databricks, or Parquet/Iceberg on S3). If we can't read it where it lives, we're asking them to build an ETL pipeline before evaluating the solution.
Production quality A reusable generic framework, not a customer-specific proof of concept. This should work for any customer with any supported data format.

Scope

✅ In Scope

  • Parquet and Iceberg table formats in Athena
  • External S3 buckets (cross-account)
  • Partition key support for large datasets
  • Optional column specification (schema inference)
  • Snowflake via Athena Federated Query
  • Schema discovery pipeline updates
  • Documentation and end-to-end validation

🔮 Out of Scope (Future)

  • Direct SDK connectors (already built separately)
  • UI for managing external connections
  • Real-time streaming from external sources
  • Write-back to external sources

Design Principle: Everything Goes Through Athena

Rather than building separate query tools for each data platform, we extend the existing Athena path. Athena already supports Parquet, Iceberg, and federated connectors natively.

Why this matters: Agents use the same query_data tool — no new tools needed. Schema discovery, join paths, and entity resolution work the same way. The orchestrator doesn't need to know whether a table is local CSV or external Snowflake.

Component Changes

1. Table Definition Schema (cdk.json)

The new schema adds optional fields while keeping full backward compatibility. A table definition with no new fields behaves exactly as it does today.

Current Format

{
  "tableName": "players",
  "s3DataPath": "data/.../kb_players.csv",
  "columns": [
    {"name": "player_id", "type": "string"},
    {"name": "username", "type": "string"}
  ]
}
→

New Format (External Parquet) 

{
  "tableName": "player_sessions",
  "description": "Session data from customer S3",
  "format": "parquet",
  "location": {
    "type": "s3",
    "bucket": "customer-data-lake-prod",
    "prefix": "game-analytics/sessions/",
    "accountId": "111122223333"
  },
  "columns": [],
  "partitionKeys": [
    {"name": "event_date", "type": "date"},
    {"name": "region", "type": "string"}
  ],
  "schemaInference": true
}
New Field Required Default Purpose
format No csv Table format: csv, json, parquet, iceberg
location No Internal bucket Where the data lives. If omitted, uses the solution's own S3 bucket
location.type If location set — s3 for direct access, federated for Glue Connector
location.bucket If s3 — S3 bucket name
location.prefix If s3 — S3 key prefix
location.accountId No Same account Cross-account bucket owner
location.connectorName If federated — Glue Connector name for Snowflake/Databricks
location.connectionProperties If federated — Connector-specific config
partitionKeys No None Partition columns for Hive-style partitioned data
schemaInference No false If true + columns empty, infer schema from data files
description No None Human-readable description, included in Schema KB

2. Glue Catalog Changes (analytics.ts)

Format Glue SerDe / Table Type Status
csv OpenCSVSerde Existing ✓
json JsonSerDe Existing ✓
parquet ParquetHiveSerDe New
iceberg table_type=ICEBERG table property New

If location is set, use the specified bucket/prefix. If partitionKeys is set, register them. If schemaInference is true and columns are empty, let the SerDe infer from data files.

3. IAM and Cross-Account Access (agents/index.ts)

  • Scan table definitions for unique external location.bucket values
  • Add s3:GetObject and s3:ListBucket scoped to each external bucket prefix
  • For cross-account buckets: customer adds a bucket policy granting our role access
  • For KMS-encrypted buckets: customer grants kms:Decrypt to our role

4. Schema Discovery Pipeline Updates

  • Schema Agent: Include source location and format metadata in generated docs
  • Schema KB: External table docs indexed alongside internal tables — no separate KB
  • Neptune graph: External tables appear with join paths to internal tables
  • Bug fix: Schema lookup currently assumes all tables are in the liveops store — update to search all registered tables regardless of location

5. Snowflake Integration (Federated Query)

First external platform connector using the Athena Snowflake Connector:

Component What's Needed
Connector Lambda Deploy the Athena Snowflake Connector as a Lambda function
Glue Registration Register connector in the Glue catalog
Secrets Manager Store Snowflake credentials (prefix: liveops/external/)
IAM Grant connector Lambda access to the secret
Networking NAT Gateway for outbound access to Snowflake API (~$32/mo)

Example configuration:

{
  "tableName": "sf_player_revenue",
  "description": "Revenue data from customer Snowflake warehouse",
  "format": "federated",
  "location": {
    "type": "federated",
    "connectorName": "snowflake-connector",
    "connectionProperties": {
      "secretName": "<your-secret-name>",
      "database": "GAME_ANALYTICS",
      "schema": "PUBLIC",
      "table": "PLAYER_REVENUE"
    }
  },
  "columns": [
    {"name": "player_id", "type": "string"},
    {"name": "revenue_usd", "type": "decimal(10,2)"},
    {"name": "transaction_date", "type": "date"}
  ]
}
Why Athena Federation over direct SDK? The agent uses the same query_data tool, the same Athena SQL, and the same schema discovery. No new tool code, no new agent config pattern, no orchestrator changes. The tradeoff is a small latency overhead from the federation hop, but for analytics queries this is acceptable.

Risks and Mitigations

Risk Impact Mitigation
Cross-account S3 access is complex for customers (bucket policy + KMS) Customer setup friction Step-by-step docs with copy-paste IAM/bucket policies
Athena Federation to Snowflake adds 3–10s latency Slower responses Acceptable for analytics; document expected latency
Schema inference for Parquet may produce unexpected types Incorrect query generation Default schemaInference to false; recommend explicit columns for production
Snowflake connector Lambda cold starts First query slow Keep-alive schedule or accept one-time cold start per session

What This Doesn't Change

Zero impact on existing deployments: Existing CSV/JSON tables work exactly as before. The agent runtime (Python) is unchanged. The orchestrator is unchanged. The UI is unchanged. Agents that don't reference external tables are unaffected.

Open Questions for Review

1Databricks connector priority

Should we add the Athena Databricks Connector in this phase, or defer? The pattern is identical to Snowflake (different connector Lambda, same config shape).

2Table registration UX

Should external tables be defined in cdk.json (requires redeploy) or should we extend the Config API to accept table definitions at runtime (more flexible, more work)?

3Cost guardrails

Should we add Athena query cost limits for external tables? Federated queries can scan large datasets. A per-query byte limit or timeout might be prudent.
